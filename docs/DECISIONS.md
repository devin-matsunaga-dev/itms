# DECISIONS.md — Decision Log

> One line per settled choice: "chose X over Y because Z (WP-N.N, YYYY-MM-DD)". Appended by Claude Code at the end of every session. Never relitigated without a work package.

## Bootstrap

- Chose a modular monolith over microservices because V1 has one team, one database, and heavy cross-module querying; module boundaries are enforced in code so extraction stays possible (bootstrap, 2026-08-28)
- Chose an in-process bus with a transactional outbox over a message broker because V1 has one deployable host and the outbox provides the needed durability and the future seam (bootstrap, 2026-08-28)
- Chose plain PostgreSQL over TimescaleDB for monitoring history because raw-30-days plus hourly rollups is sufficient at this scale and is one less thing to operate; revisit only if measured (bootstrap, 2026-08-28)
- Chose a separate Python poller over in-process .NET polling because icmplib/pysnmp are the better tools and polling load must never stall the web host (bootstrap, 2026-08-28)
- Chose cookie auth with server-side sessions over browser-held JWTs because it allows real revocation and keeps no token in browser storage (bootstrap, 2026-08-28)
- Chose to move minimal departments and locations into Phase 0, ahead of the spec's stated order, because users and assets cannot be created without them and backfilling would touch every seed and form (bootstrap, 2026-08-28)
- Chose to move the audit spine into Phase 0, ahead of the spec's stated order, because auditing is an event consumer and retrofitting it after ten modules means revisiting all ten (bootstrap, 2026-08-28)
- Chose platform versions pinned to LTS or latest-supported — .NET 10, Aspire 13.x, Node 24, Python 3.13+, React 19, PostgreSQL 17+ (bootstrap, 2026-08-28)
- Chose Tailwind + shadcn/ui + lucide + Recharts as the UI stack, themed to the reference screenshot at docs/design/reference-dashboard.png (bootstrap, 2026-08-28)
- Chose the human as the merge gate: Claude Code branches and builds, never merges, pushes, or tags (bootstrap, 2026-08-28)

## WP-0.1 — Solution skeleton

- Chose xUnit v3 with Shouldly over xUnit v2 with FluentAssertions because v3 is the current xUnit line and FluentAssertions v8 is commercially licensed for non-open-source use, which this project would trip (WP-0.1, 2026-08-28)
- Chose the Microsoft.Testing.Platform runner, selected in `global.json`, over VSTest because xUnit v3 is an MTP runner and the .NET 10 SDK refuses to drive one through the VSTest target at all (WP-0.1, 2026-08-28)
- Chose central package management in `Directory.Packages.props` over per-project versions because CONVENTIONS.md requires near-empty `.csproj` files and two projects must never be able to disagree about a version (WP-0.1, 2026-08-28)
- Chose the classic `ITMS.sln` format over the .NET 10 SDK's new `.slnx` default because CONVENTIONS.md and WP-0.1 both name `ITMS.sln`; migrating later is one command plus a CONVENTIONS.md edit (WP-0.1, 2026-08-28)
- Chose an `AssemblyMarker` type in every library over locating assemblies by name string because the architecture tests and convention-based registration then fail at compile time when a project is renamed or dropped, not at runtime (WP-0.1, 2026-08-28)
- Chose to enable `EnforceCodeStyleInBuild` but elevate only the file-scoped-namespace rule to error, leaving other style rules at suggestion, because `TreatWarningsAsErrors` turns any warning-level style rule into a build break and a skeleton that fails on cosmetics is one nobody can extend (WP-0.1, 2026-08-28)
- Chose to disable CA1707 under `tests/` only, because underscored test names are how the suite stays readable and the rule is aimed at public API surface (WP-0.1, 2026-08-28)
- Chose to pin Aspire at 13.5.3 via the AppHost SDK attribute rather than a floating version because ARCHITECTURE.md §10 makes `aspire update` an explicit phase-gate step (WP-0.1, 2026-08-28)

## WP-0.2 — Aspire orchestration

- Chose to pin container image tags (`postgres:17.6`, `redis:7.4`, `mailhog/mailhog:v1.0.1`) over floating the Aspire defaults because ARCHITECTURE.md §10 requires a dev machine and a production compose file to run the same version, and a silent minor bump is the kind of drift nobody notices until it breaks (WP-0.2, 2026-08-28)
- Chose `ContainerLifetime.Persistent` plus named data volumes for PostgreSQL and Redis over recreating them each run because migrations and seed data have to survive a session, and container startup is the slowest part of `aspire run` (WP-0.2, 2026-08-28)
- Chose to leave MailHog session-lifetime and volume-less over persisting captured mail because it is dev SMTP capture with nothing worth keeping across a restart, and a maildir volume is one more thing to reason about (WP-0.2, 2026-08-28)
- Chose MailHog as a plain `AddContainer` resource over adopting `CommunityToolkit.Aspire.Hosting.MailPit` because ARCHITECTURE.md §10 and WP-0.2 both name MailHog; MailHog being archived upstream is recorded in STATUS.md as a swap to consider before the Notifications module depends on it (WP-0.2, 2026-08-28)
- Chose Redis 7.4 over 8.x because ARCHITECTURE.md pins PostgreSQL but is silent on Redis, and 7.4 is the Aspire default and the conservative choice for V1 (WP-0.2, 2026-08-28)
- Chose to have `Itms.Web.Host` actually consume the Aspire connection strings via `Aspire.Npgsql` and `Aspire.StackExchange.Redis` over merely receiving them because an unconsumed connection string proves nothing and leaves `/health` green while PostgreSQL is down; verified by stopping each container and watching `/health` return 503 (WP-0.2, 2026-08-28)
- Chose to bind the MailHog SMTP endpoint to `Smtp__Host`/`Smtp__Port` configuration keys over Aspire's `WithReference` service-discovery variables because SMTP has no connection-string convention and the Notifications module will read plain configuration (WP-0.2, 2026-08-28)
- Chose to leave the ServiceDefaults health endpoints Development-only rather than exposing them in production, because opening them is a security decision that belongs to Phase 6 and not to an orchestration package (WP-0.2, 2026-08-28)
- Chose to test the Aspire application model with `Aspire.Hosting.Testing` in Publish mode over starting the distributed application because Publish mode resolves connection strings to unresolved expressions, so the wiring is asserted without a Docker daemon and the suite stays inside the two-minute budget in CONVENTIONS.md (WP-0.2, 2026-08-28)
- Chose to assert configuration hygiene with a test that scans every checked-in `appsettings*.json` over trusting review because "no connection strings in the repository" is a rule that only holds if something enforces it (WP-0.2, 2026-08-28)

## WP-0.3 — Platform & Contracts

- Chose two independent sealed types, `Result` and `Result<T>`, over `Result<T> : Result` because CONVENTIONS.md says sealed by default and an inheritance root would let a future subclass redefine what success means (WP-0.3, 2026-08-29)
- Chose an `ErrorKind` enum mapped to HTTP in one place over handlers choosing status codes because ARCHITECTURE.md §6 says errors are ProblemDetails *always*, and "always" only survives forty endpoints if the translation lives in a single file (WP-0.3, 2026-08-29)
- Chose to put the ProblemDetails mapping and the validation endpoint filter in `Itms.Platform`, giving the shared kernel a `FrameworkReference` on `Microsoft.AspNetCore.App`, over a separate web-primitives project because the kernel still references no module and a fourth shared project would be ceremony (WP-0.3, 2026-08-29)
- Chose to clamp out-of-range paging input rather than reject it because a caller asking for page 0 wants results, not a 400, and the clamp is also what stops a hostile `pageSize` becoming a table scan (WP-0.3, 2026-08-29)
- Chose to camel-case FluentValidation's property names before returning them so the client maps errors straight onto form fields, over returning CLR names and translating per form (WP-0.3, 2026-08-29)
- Chose to treat a missing `IValidator<T>` as "no rules" rather than a failure because not every request model needs validation and failing closed would make adding an endpoint a two-step affair (WP-0.3, 2026-08-29)
- Chose a hand-written RFC 4180 `CsvParser` returning `Result` over CsvHelper because the import surface is two files (SPEC.md §12) and a malformed upload must come back as a ProblemDetails, not as an exception from someone else's parser; noted in STATUS.md as swappable if requirements grow (WP-0.3, 2026-08-29)
- Chose to neutralise leading `=`, `+`, `-`, and `@` in exported CSV fields because exported ticket and asset text is attacker-controlled and the export is the only place spreadsheet formula injection can be stopped (WP-0.3, 2026-08-29)
- Chose to enforce the §3 boundary rules from both the `.csproj` graph and the compiled assembly references because the modules are still empty and the C# compiler omits a project reference it sees no types from — the declared-reference check is the one that bites today (WP-0.3, 2026-08-29)
- Chose to write only the four lookup contracts that ARCHITECTURE.md's cross-module reads actually imply — asset, user, department, location — and to leave `ITicketLookup` and `IDeviceLookup` to the package that first needs one, because speculative contracts rot (WP-0.3, 2026-08-29)
- Chose to carry denormalised display text (ticket number, asset tag, location path) on domain events rather than have consumers look it up, per §3 rule 6, so a consumer can render without a cross-module call and an alert keeps the context it was raised with (WP-0.3, 2026-08-29)
- Chose `Guid.CreateVersion7()` for event ids over `Guid.NewGuid()` because the outbox table will be indexed on the id and v7 is time-ordered, which keeps that index from fragmenting (WP-0.3, 2026-08-29)
- Chose to disable CA1716 repo-wide over renaming `Error` because the rule protects cross-language consumers this C#-only solution will never have, and it would otherwise push good domain names into worse ones at every module (WP-0.3, 2026-08-29)
- Chose to wire `AddPlatform()` plus `UseExceptionHandler`/`UseStatusCodePages` into `Itms.Web.Host` in this package because an unregistered shared kernel proves nothing and framework-generated 404s would otherwise not be ProblemDetails (WP-0.3, 2026-08-29)

## WP-0.4 — In-process bus + transactional outbox

- Chose a separate `Itms.Messaging` project over putting the bus in `Itms.Platform` because publishing takes a `DomainEvent` from `Itms.Contracts`, and WP-0.3 deliberately keeps the shared kernel clear of Contracts so a cross-module read never drags the kernel along (WP-0.4, 2026-08-29)
- Chose to treat messaging as infrastructure rather than a module — its own `messaging` schema, its own migrations history, no module may reference it — because it owns no business data, and ARCHITECTURE.md §4's one-schema-per-module rule is about ownership (WP-0.4, 2026-08-29)
- Chose a scoped `IDbSession` owning one connection per scope, with every `DbContext` built on it, over each context opening its own because "the publisher enrols in the caller's transaction" is otherwise two transactions and a window between them (WP-0.4, 2026-08-29)
- Chose to throw when `PublishAsync` is called outside a transaction over publishing immediately, because a lone publish silently reintroduces the exact failure the outbox exists to remove and is a programming error, not a failure the caller can act on (WP-0.4, 2026-08-29)
- Chose a lease-based claim — one `FOR UPDATE SKIP LOCKED` statement that pushes `available_at` forward and commits — over holding a row lock across the consumers, because one slow consumer would otherwise block a whole batch and a crashed dispatcher would block it until the connection died (WP-0.4, 2026-08-29)
- Chose one transaction per consumer, committing the consumer's work and its consumption row together, over one transaction per message, because that is what makes a partial failure retry only the consumer that threw (WP-0.4, 2026-08-29)
- Chose a `(message_id, consumer_name)` composite primary key as the idempotency ledger over a processed flag on the message, because two consumers of one event must be tracked separately and the database itself then refuses a duplicate (WP-0.4, 2026-08-29)
- Chose to name consumption rows after the implementation type rather than the interface, so renaming a consumer makes it re-consume history rather than silently inherit another consumer's completions — the safe direction of that mistake (WP-0.4, 2026-08-29)
- Chose to park a message after `MaxAttempts` rather than delete it, and to leave no requeue path in this package, because a dead-lettered event is evidence and reviving one should be a deliberate operator act (WP-0.4, 2026-08-29)
- Chose to leave a message whose event type this build does not know outstanding — refunding the attempt — over dead-lettering it, because a rolling deployment can put a newer build's message in front of an older dispatcher and that is a wait, not a poisoning (WP-0.4, 2026-08-29)
- Chose `IEventConsumer<T>`/`ConsumeAsync` over `IEventHandler<T>`/`HandleAsync` because CA1711 reserves the `EventHandler` suffix for delegates, and "consumer" is the word ARCHITECTURE.md §5 already uses — a rename was cheaper than a repo-wide suppression (WP-0.4, 2026-08-29)
- Chose to keep `Aspire.Npgsql` (the bare `NpgsqlDataSource`) over swapping to `Aspire.Npgsql.EntityFrameworkCore.PostgreSQL` because every context is built on the connection `IDbSession` hands out, so an Aspire-registered context with a pool of its own would defeat the shared transaction; this supersedes the swap STATUS.md anticipated at WP-0.2 (WP-0.4, 2026-08-29)
- Chose source-generated `[LoggerMessage]` partials over `logger.LogXxx` calls because the repo builds warnings-as-errors and CA1848 is right about the dispatcher being a hot path (WP-0.4, 2026-08-29)
- Chose to split `IOutboxProcessor.ProcessOnceAsync` out of the hosted service so tests drive delivery a pass at a time, rather than starting the background loop and waiting on it, which CONVENTIONS.md's ban on `Thread.Sleep` in tests rules out anyway (WP-0.4, 2026-08-29)
- Chose to have the integration-test consumers write rows to a real table through the ambient session over counting in-memory invocations, because the latter would pass even if the consumption row and the side effect committed separately (WP-0.4, 2026-08-29)
- Chose an `Itms.TestSupport` project holding `FakeClock` and the Testcontainers/Respawn fixture over duplicating them, because STATUS.md ruled out `Itms.IntegrationTests` referencing `Itms.UnitTests` and a test project referencing another test project makes one suite's refactor the other's build break (WP-0.4, 2026-08-29)
- Chose to relax IDE0161 (file-scoped namespaces) to a suggestion under `**/Migrations/` because EF Core generates block namespaces and ARCHITECTURE.md §4 says a migration is never edited after merge (WP-0.4, 2026-08-29)

## WP-0.5 — Identity, roles, cookie auth

- Chose to declare `IModuleDbSession` in `Itms.Platform` and adapt it onto the bus's `IDbSession` in the composition root, over letting a module reference `Itms.Messaging` or letting a module context open its own connection, because a module that cannot see the ambient connection cannot commit its change and its outbox event together — and the boundary rule that forbids the reference is the one the architecture tests enforce (WP-0.5, 2026-08-29)
- Chose a `sessions` table checked on every request over Identity's security-stamp validation interval, because ARCHITECTURE.md §7 promises revocation and revocation that takes effect in thirty minutes is not revocation; the cost is one indexed single-row query per authenticated request (WP-0.5, 2026-08-29)
- Chose to put sessions in PostgreSQL rather than Redis because §4 says nothing in Redis is a source of truth and the system must survive a flush — a flush that silently signed everybody back in would be the opposite of a revocation store (WP-0.5, 2026-08-29)
- Chose not to write a `last_seen_at` column on the session row, because it would turn every authenticated GET into a write; the cookie's sliding expiry keeps an active session alive and `expires_at` is the absolute ceiling on top of it (WP-0.5, 2026-08-29)
- Chose `AddIdentityCore` plus an explicitly configured cookie handler over `AddIdentity`, because the latter registers external-login and two-factor schemes this system does not have and would have made `SignOutAsync` fail on a scheme that was never configured (WP-0.5, 2026-08-29)
- Chose to answer an unauthenticated request with 401 and a forbidden one with 403 by overriding the cookie handler's redirect events, over leaving the framework default, because a 302 to an HTML login page would leave a `fetch` call parsing markup as though it were data (WP-0.5, 2026-08-29)
- Chose one generic message for "no such account", "wrong password", and "deactivated", and a distinct one only for lockout, because anything finer turns the login form into a directory of who has an account here — while lockout is a state the account holder has to be able to understand and the attacker who caused it already knows (WP-0.5, 2026-08-29)
- Chose to accept either the user name or the email address at sign-in because both are unique and people remember their address more reliably (WP-0.5, 2026-08-29)
- Chose to move Identity's user-name claim to `ClaimTypes.Upn` and put the display name in `ClaimTypes.Name` via a custom claims principal factory, over editing `Itms.Platform`'s `HttpContextCurrentUser`, because the kernel should not have to know how a principal is minted and every audit row and ticket would otherwise show `tech` instead of a person's name (WP-0.5, 2026-08-29)
- Chose to have a password change revoke every *other* session while keeping the caller's, over revoking all of them, because the password is usually changed precisely because the old one may be known to someone else, and signing the user out of the browser they just used adds nothing (WP-0.5, 2026-08-29)
- Chose to run the password change and the revocations in one transaction, because a crash between them would leave the old password dead and the sessions it protected alive (WP-0.5, 2026-08-29)
- Chose to build the CSRF antiforgery check and the login rate limit now rather than leave both to `WP-6.1 — Security hardening`, because CONVENTIONS.md's security floor requires them of any cookie-auth endpoint and WP-0.5 is where cookie auth arrives; WP-6.1 verifies and extends them instead of building them (WP-0.5, 2026-08-29)
- Chose to validate antiforgery in an explicit endpoint filter over `UseAntiforgery`, because minimal APIs validate automatically only for form-bound endpoints and these take JSON — and login CSRF, which needs no existing session, is the attack that matters most here (WP-0.5, 2026-08-29)
- Chose to partition the credential rate limit by address rather than by account, because the attack lockout cannot see is one source trying many accounts (WP-0.5, 2026-08-29)
- Chose explicit `IEntityTypeConfiguration<T>` files for the framework-owned Identity tables too, over a reflection pass that snake_cases the whole model, because CONVENTIONS.md asks for one per entity and a generated naming pass is invisible in review (WP-0.5, 2026-08-29)
- Chose to leave `created_at`/`created_by` off the framework-owned join and claim tables, because `UserManager` writes them and has nowhere to put an actor; who changed a role is recorded in the audit log, where ARCHITECTURE.md §8 says it belongs (WP-0.5, 2026-08-29)
- Chose to map `user_logins` rather than ignore the entity, even though V1 has local accounts only, because `UserStore` queries it while deleting a user and an unmapped table would turn that into a runtime error the first time an administrator removes an account (WP-0.5, 2026-08-29)
- Chose to seed roles in every environment but development accounts only in Development, with the environment check inside the seeder rather than only at the call site, because the accounts carry a documented password and an environment check is the only thing between a convenience and a back door (WP-0.5, 2026-08-29)
- Chose to implement `IUserLookup` in this package rather than defer it to the first module that reads a user, because Identity owns users, the record shape was already settled in WP-0.3, and the contract needed proving against a real table (WP-0.5, 2026-08-29)
- Chose to add read-only `GET /api/v1/users` and `GET /api/v1/users/{id}` under the Technician policy, slightly ahead of the package's text, because every later module needs a requester and assignee picker and the role matrix needed a real role-guarded endpoint to be enforced on; user administration remains WP-5.8 (WP-0.5, 2026-08-29)
- Chose to boot the real host with `Microsoft.AspNetCore.Mvc.Testing` rather than assert authentication against a hand-built service provider, because every WP-0.5 criterion is a statement about what the wire carries; this pulls forward the dependency STATUS.md had pencilled in for WP-0.9 (WP-0.5, 2026-08-29)
- Chose a second *database* inside the shared container for the web-host suite, over a second container or a shared database, because CONVENTIONS.md wants one container per assembly but the host runs the outbox dispatcher, which would claim the messages the outbox tests are asserting on (WP-0.5, 2026-08-29)
- Chose to pin `Microsoft.EntityFrameworkCore.Relational` at 10.0.4 rather than 10.0.3, because `Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.3 requires it and central transitive pinning turns the mismatch into an NU1605 restore failure (WP-0.5, 2026-08-29)
- Chose to relax CA1861 under `**/Migrations/` alongside IDE0161, because EF generates a composite index's column list inline and hand-hoisting it to a static field is the edit ARCHITECTURE.md §4 says must never become a habit (WP-0.5, 2026-08-29)

## WP-0.6 — Minimal directory (departments & locations)

- Chose two materialised path columns on every location — `path` (ids) and `full_path` (display text) — over a recursive CTE or an adjacency walk, because `LocationSummary.Path` is read on every alert, ticket, and asset row and the WP's "queries a full path efficiently" means one indexed row read, not one query per level (WP-0.6, 2026-08-31)
- Chose to pay for that on writes: a rename or a move rewrites its subtree in one prefix `UPDATE` inside the same transaction, because renames are rare and reads are constant, and a half-rewritten subtree would be worse than a slow one (WP-0.6, 2026-08-31)
- Chose to select the subtree by the id path rather than the display path, because a sibling named "Head Office Annex" starts with "Head Office" and a display-path prefix match would drag it along (WP-0.6, 2026-08-31)
- Chose `varchar_pattern_ops` on the `path` index because the database collation is not C, and without the operator class every `LIKE 'prefix%'` — every subtree read and every rename — would fall back to a sequential scan (WP-0.6, 2026-08-31)
- Chose "the child's rank is strictly below the parent's" over "exactly one level below", because SPEC.md §5 names pump stations and remote facilities, and requiring a building and a floor before a cabinet would force operators to invent placeholder nodes (WP-0.6, 2026-08-31)
- Chose `Floor` and `Area` as two labels of one rank, per SPEC.md §5's "Floor/Area", so neither can contain the other (WP-0.6, 2026-08-31)
- Chose `" / "` as the display-path separator over the arrow SPEC.md draws the hierarchy with, because the value lands in table cells and CSV exports and an arrow survives neither (WP-0.6, 2026-08-31)
- Chose to retire departments rather than delete them, and to ship no `DELETE` route for one, because `DepartmentSummary.IsActive` is documented as keeping existing references resolvable and §3 rule 6 leaves no foreign key that could tell Directory whether a ticket still points at the row (WP-0.6, 2026-08-31)
- Chose to refuse deleting a location with children rather than cascade, and to set the `parent_id` foreign key to `Restrict` as well, because one mistaken click would otherwise remove a site and every room the assets and alerts reference (WP-0.6, 2026-08-31)
- Chose normalised `normalized_name`/`normalized_code` columns carrying the unique indexes over expression indexes on `lower(...)`, because the constraint then appears in the EF model where review can see it, and it is the shape Identity already uses (WP-0.6, 2026-08-31)
- Chose `AreNullsDistinct(false)` on the location sibling index because PostgreSQL's default treats two null parents as distinct, which would let two roots share a name (WP-0.6, 2026-08-31)
- Chose to store `LocationKind` as text rather than an integer because a directory row is read in psql during an incident far more often than an enum is renumbered (WP-0.6, 2026-08-31)
- Chose reads under the Authenticated policy and writes under Admin, rather than putting the whole module behind Technician, because an end user filing their own ticket has to pick a department and a room, while SPEC.md §13 puts managing them under administration (WP-0.6, 2026-08-31)
- Chose to put the antiforgery endpoint filter in `Itms.Platform` rather than reuse the Identity one, because a module may not reference another module and every module that writes behind a cookie needs it; Identity's copy was deliberately left untouched under the standing rule and the two should collapse at WP-6.1 (WP-0.6, 2026-08-31)
- Chose to keep the depth guard even though the rank rule already makes it unreachable, because it is what keeps the materialised path inside its column the day a sixth kind is added (WP-0.6, 2026-08-31)
- Chose to seed the development directory in Development only, unlike the roles Identity seeds everywhere, because a department is business data and inventing "Finance" for somebody's actual organisation is worse than starting blank (WP-0.6, 2026-08-31)
- Chose to extend the existing `IdentityWebFixture` with the `directory` schema rather than boot a second host, because the fixture already boots the whole composition root and a second one would duplicate the factory and the startup cost (WP-0.6, 2026-08-31)
- Chose not to re-seed the development directory in `ResetAsync`, so a directory test starts from an empty tree and builds exactly what it asserts on; the seeder has its own test instead (WP-0.6, 2026-08-31)
- Chose `Itms.*Tests.DirectoryModule` as the test namespace rather than `.Directory`, because the latter shadows `System.IO.Directory` and broke an existing WP-0.2 test the moment it appeared (WP-0.6, 2026-08-31)

## WP-0.7 — Audit spine

- Chose to move `IEventConsumer<T>` from `Itms.Messaging.Abstractions` into `Itms.Contracts` over letting the Audit module reference the bus or putting host-side adapter classes in the composition root, because declaring a reaction is a cross-module integration concern and a module may not reference `Itms.Messaging` — as written, no module could have declared a consumer at all (WP-0.7, 2026-08-31)
- Chose `Itms.Contracts.Messaging` as its namespace rather than `Itms.Contracts.Events`, because `ContractShapeTests` asserts that namespace holds exactly the eleven events and the base type, and a consumption contract is not itself a fact about anything (WP-0.7, 2026-08-31)
- Chose to leave `IEventPublisher` in the bus for now, because nothing in this package publishes; the first module that raises an event hits the identical wall and moves it the same way, and that is recorded in STATUS.md rather than done speculatively (WP-0.7, 2026-08-31)
- Chose one consumer class implementing `IEventConsumer<T>` eleven times over eleven classes, because the dispatcher keys consumption on the consumer name and one name gives the whole trail one idempotency key and one retry story (WP-0.7, 2026-08-31)
- Chose explicit interface implementations for those eleven methods over public overloads, because they differ only in their parameter type and an overload set of that shape invites a call to the wrong one (WP-0.7, 2026-08-31)
- Chose a coverage test that fails the build when an event in `Itms.Contracts` has no binding on the consumer, over trusting the list to be maintained, because an unaudited event is indistinguishable from an event nothing has published yet and no other test would notice (WP-0.7, 2026-08-31)
- Chose to write the event-to-entry mapping out by hand over reflecting across the event's properties, because every event names its subject differently — `TicketId`, `AssetId`, `DeviceId`, `AlertId` — and a reflection pass would have to guess which property is the entity and which is carried display text (WP-0.7, 2026-08-31)
- Chose to take the actor and the instant from the event rather than from `ICurrentUser` on event-derived rows, because the dispatcher runs on a background scope with no principal and a backlog must not rewrite when things happened (WP-0.7, 2026-08-31)
- Chose to leave the source IP null on event-derived rows over inventing one, because the event carries no request context; adding a source-IP field to `DomainEvent` would touch every future publisher and is recorded in STATUS.md as `WP-6.1`'s decision (WP-0.7, 2026-08-31)
- Chose one internal `AuditRecorder` as the only write path, shared by `IAuditWriter` and the event consumer, over two independent writers, because "how does a row get into that table" should have one answer (WP-0.7, 2026-08-31)
- Chose to have the writer join the caller's transaction when there is one and open its own when there is not, because a rolled-back change must leave no entry claiming it happened, while a failed sign-in changes nothing and the entry is the only evidence it occurred (WP-0.7, 2026-08-31)
- Chose an `AuditDbContext` that exposes no `DbSet` — only `Query()` and `AppendAsync()` — because a `DbSet<AuditRecord>` property hands every caller `Remove`, `RemoveRange`, `ExecuteDelete`, and `ExecuteUpdate`, and invariant 10 says none of those may exist (WP-0.7, 2026-08-31)

## WP-1.8 — Basic SLA

- Chose to store both deadlines and both 80% marks as instants on the ticket, over storing elapsed time or a swept flag, because every question the system asks — is this breached, order the queue by what is due soonest, filter the overdue view — then becomes a column comparison the database can answer in the query that reads the row (WP-1.8, 2026-09-01)
- Chose to snapshot the priority's two targets onto the ticket at creation, so editing a priority's targets moves the tickets filed afterwards and no others, because a ticket has to keep the promise made when it was raised — the same point-in-time reasoning WP-1.4 applied to history values, against WP-1.1's by-id propagation for names (WP-1.8, 2026-09-01)
- Chose to pause and resume the resolution clock inside `Ticket.Move`, the private mover every transition already goes through, over having each handler do it, because "Waiting pauses the resolution clock" is an invariant of the ticket and a handler that has to remember can be merged having forgotten — the call WP-1.4 made for history entries (WP-1.8, 2026-09-01)
- Chose to move the two resolution instants forward by the length of each pause, over accumulating a debt subtracted at read time, because a moved deadline stays a plain indexable column while a debt would have to be applied to every row of every query (WP-1.8, 2026-09-01)
- Chose to judge a parked resolution clock at the instant it was parked, in both the assessment and the SQL filter, because the stored deadline is frozen for the length of the pause and comparing it against a moving `now` would let a ticket drift into a breach while nobody is able to work on it (WP-1.8, 2026-09-01)
- Chose to make a running clock breach at `>= due` and a stopped one at `> due`, because a four-hour target promises the work done *within* four hours and four hours exactly is within, while a deadline that has arrived with nothing done is late (WP-1.8, 2026-09-01)
- Chose `Approaching` at `>= warn`, so 80% consumed is the flag point rather than the first tick past it, following SPEC.md §2's wording (WP-1.8, 2026-09-01)
- Chose to compute the 80% mark in integer ticks as `× 80 ÷ 100`, over floating-point `× 0.8`, because binary floating point cannot hold 0.8 and an 80% boundary landing a tick either side of where a test puts it is a flake; it also makes the mark a whole number of seconds for any whole-minute target, which is what lets the migration's backfill compute the identical instant in SQL (WP-1.8, 2026-09-01)
- Chose to stop the response clock on the first public comment from anybody but the requester, or on the resolution if that comes first, and explicitly **not** on assignment, at the human's direction, because being handed a ticket is not answering the person who raised it (WP-1.8, 2026-09-01)
- Chose to make `responded_at` write-once and to leave it set through a reopen, because a response did happen and reopening does not unmake it (WP-1.8, 2026-09-01)
- Chose not to move `updated_at` when a comment stamps the response, because bumping it on the first public comment and on no other would make "last updated" mean two different things in one column (WP-1.8, 2026-09-01)
- Chose to stop a cancelled ticket's SLA with no outcome — `Stopped`, neither met nor breached — at the human's direction, over freezing an evaluation against `updated_at`, because that column moves for unrelated reasons; a package that needs cancellation to carry an outcome adds an explicit `cancelled_at` (WP-1.8, 2026-09-01)
- Chose to let time spent in Resolved count against the resolution target, at the human's direction, because SPEC.md pauses for Waiting and nothing else — so a reopened ticket can come back already breached rather than a second implicit pause being invented (WP-1.8, 2026-09-01)
- Chose to carry `IsPaused` as a fact alongside the state rather than as a sixth `SlaState` value, because a ticket can be parked *and* already breached and a state of "paused" would hide the breach a technician needs to see (WP-1.8, 2026-09-01)
- Chose to make `due_at` `NOT NULL`, held empty since WP-1.2, because every ticket has a priority and every priority carries a resolution target — which also retires the nulls-last branch in the due-date sort (WP-1.8, 2026-09-01)
- Chose to add the five required SLA columns nullable, backfill each ticket from its own priority, and only then set `NOT NULL`, over the scaffolded single-step default, because a default deadline of `0001-01-01` would have left every existing ticket claiming it was due two thousand years ago (WP-1.8, 2026-09-01)
- Chose to have the backfill reconstruct the clocks as though nothing had ever been paused, over replaying WP-1.4's history to recover those spans, because that is a great deal of machinery for tickets raised before the feature existed (WP-1.8, 2026-09-01)
- Chose to ship `Ticket.RetargetSla` with no production caller rather than the priority-change endpoint that would use it, because STATUS.md has recorded that path as unowned since WP-1.4 and an endpoint needs an audit decision and possibly an event ARCHITECTURE.md §5 does not list; the method is where the criterion's "priority changes mid-flight" is tested, and its remarks name the obligation on whichever package adds the path (WP-1.8, 2026-09-01)
- Chose to re-cut both deadlines from creation on a retarget, rather than from the moment of the change, because SPEC.md §2 measures a target against ticket creation — a ticket raised at nine and promoted at eleven was always a ticket raised at nine, so promoting a long-running one can breach it immediately (WP-1.8, 2026-09-01)
- Chose to add `slaState` to the queue filter in this package, at the human's direction, rather than leave WP-1.9 to change the API contract to render its named "Overdue" view, following the precedent WP-1.5 set by shipping `unassigned` ahead of the same UI package (WP-1.8, 2026-09-01)
- Chose to accept that the SLA rule now exists twice — `SlaAssessment` in memory and `TicketSlaFilter` in SQL — because one runs over a materialised row and the other must reach PostgreSQL as an expression tree, and to guard the pair with a test asserting that every row the filter returns for a state describes itself as being in that state (WP-1.8, 2026-09-01)
- Chose a nested `sla` object on the list and detail payloads while leaving top-level `dueAt` where WP-1.5 put it, so the queue keeps sorting on the field it already carries and the SLA reads on its own (WP-1.8, 2026-09-01)
- Chose to send the accumulated pause as `pausedSeconds`, an integer, rather than a `TimeSpan`, because nothing else in this API sends a duration and a .NET `TimeSpan` reaches a client as a string it has to parse (WP-1.8, 2026-09-01)
- Chose to put the SLA targets on `NewTicket` rather than add a parameter to `Ticket.Create`, because that record is invariant 1 written as a shape and a ticket must have an SLA the moment it exists — a caller cannot reach `Create` having forgotten one (WP-1.8, 2026-09-01)
- Chose to make `SlaClock`, `SlaAssessment`, `SlaTargets`, `SlaState`, and `TicketSla` public, joining the standing list with `TicketStateMachine`, `TicketHistoryRecorder`, and the WP-1.7 five, because they are pure rules CONVENTIONS.md wants unit-tested and this repository has no `InternalsVisibleTo`; `TicketSlaFilter` stayed internal and is proved through the endpoint (WP-1.8, 2026-09-01)

## WP-2.2 — Asset history

- Chose two history kinds — Assignment and Status — over one per named operation, because SPEC.md §3's five events are five operations over two dimensions, and recording the verb would leave a timeline unable to answer "who had this before?" without knowing which verb to look under (WP-2.2, 2026-09-01)
- Chose to derive the history entries and the published events from one before/after snapshot diff rather than let each handler name its own, because a handler that decides which entries its change owes is a handler that can be merged having produced none — the call WP-1.4 made for a ticket (WP-2.2, 2026-09-01)
- Chose to make a transfer `AssignTo` against an asset somebody already holds rather than a sixth domain method, because it is the same fact with a from-value and two routes to one column is two chances to forget the history entry (WP-2.2, 2026-09-01)
- Chose to make Retired, Lost and Disposed terminal, at the human's direction, because that is WP-1.3's reading of SPEC.md's silence and an explicit correction workflow is better than inventing recovery semantics the spec does not define (WP-2.2, 2026-09-01)
- Chose to move an in-stock asset to Deployed when it is first issued, and back to In Stock when it is returned, at the human's direction, treating assignment and lifecycle as distinct facts — so a first issue writes two history entries at one instant and a transfer writes exactly one (WP-2.2, 2026-09-01)
- Chose to release the holder when an asset is retired, at the human's direction, because a retired asset that is still assigned claims equipment is issued which nobody can use (WP-2.2, 2026-09-01)
- Chose to land a return from repair on Deployed when a holder remains and In Stock when none does, at the human's direction, because it preserves the asset's real operational state without forcing somebody to reassign a machine that never changed hands (WP-2.2, 2026-09-01)
